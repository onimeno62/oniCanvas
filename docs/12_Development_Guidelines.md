# 12 - Development Guidelines

Version: 1.0
Status: Active

---

# Purpose

This document defines the development standards for OniCanvas.

Every contribution—whether written by a developer or generated by AI—should follow these guidelines to ensure consistency, maintainability, and long-term scalability.

---

# Development Philosophy

Build slowly.

Build correctly.

Build modularly.

Never sacrifice code quality for speed.

Every feature should leave the project in a better state than before.

---

# General Principles

Follow

- SOLID principles
- DRY (Don't Repeat Yourself)
- KISS (Keep It Simple)
- Composition over inheritance
- Single Responsibility Principle

Avoid unnecessary abstractions until there is a clear need.

---

# Architecture Rules

Use

- MVVM
- Repository Pattern
- StateFlow
- Coroutines
- Jetpack Compose
- Material 3

Business logic belongs in ViewModels and Use Cases.

UI should only render state and send user actions.

---

# Jetpack Compose Guidelines

## Composables

Should

- Be small
- Be reusable
- Be stateless whenever possible
- Accept state and callbacks as parameters

Avoid

- Database access
- Network calls
- Business logic
- Large composable functions

---

## State

Use

StateFlow

collectAsStateWithLifecycle()

Expose immutable UI state.

Avoid mutable state outside ViewModels unless it is purely UI-related.

---

## Navigation

Use

Navigation Compose

Single Activity architecture.

Navigation events should originate from the ViewModel.

# File Organization

Keep related files together.

Example

feature/dashboard/

- DashboardScreen.kt
- DashboardViewModel.kt
- DashboardUiState.kt
- DashboardEvents.kt
- DashboardComponents.kt

Avoid generic folders like "misc" or "helpers" unless absolutely necessary.

---

# Error Handling

Handle all expected errors.

Examples

- Network failures
- Invalid profiles
- Missing permissions
- Connection timeouts

Provide meaningful user feedback.

Never fail silently.

---

# Logging

Use structured logging.

Development

- Verbose logs enabled

Release

- Minimal logging
- No sensitive information

Log

- Connections
- Errors
- Important state changes

---

# Performance

Target

- 60 FPS UI
- Fast startup
- Minimal memory usage

Avoid

- Unnecessary recomposition
- Blocking the main thread
- Heavy work inside Composables

Use background threads for I/O and networking.

---

# Accessibility

Support

- Screen readers
- Dynamic text sizes
- High contrast
- Reduced motion
- Minimum 48dp touch targets

Accessibility should be considered from the beginning—not added later.

---

# Testing

## Unit Tests

Test

- ViewModels
- Use Cases
- Repositories
- Utility functions

## Integration Tests

Test

- Database interactions
- Communication protocol
- Repository behavior

## UI Tests

Test

- Navigation
- User flows
- Common interactions

Aim to test critical workflows before adding new features.

# Git Workflow

Recommended Branches

main

Stable production-ready code.

develop

Integration branch for completed features.

feature/<feature-name>

Individual feature development.

bugfix/<issue-name>

Bug fixes.

release/<version>

Release preparation.

---

# Commit Messages

Format

type: short description

Examples

feat: add macro pad screen

fix: reconnect after Wi-Fi timeout

refactor: simplify connection manager

docs: update communication protocol

chore: update dependencies

---

# Documentation

Update documentation whenever

- Features change
- Data models change
- Protocol changes
- Architecture changes

Documentation should evolve alongside the code.

---

# Dependencies

Before adding a new library

- Check if AndroidX already provides the functionality.
- Avoid duplicate libraries.
- Prefer stable, well-maintained dependencies.

Keep the dependency list as small as practical.

---

# Code Review Checklist

Before merging:

- Builds successfully
- No compiler warnings
- No obvious code duplication
- Follows architecture
- UI matches design guidelines
- Handles errors correctly
- Documentation updated
- Tested where appropriate

---

# Release Process

For each release:

1. Update version number
2. Update changelog
3. Run tests
4. Verify communication with Windows Companion
5. Test on phone and tablet
6. Build release APK/AAB
7. Tag release in version control

---

# Long-Term Maintenance

As OniCanvas grows:

- Prefer extending existing systems over creating parallel ones.
- Remove dead code.
- Refactor when patterns emerge.
- Keep features modular.
- Maintain backward compatibility where practical.

---

# Summary

These guidelines are intended to keep OniCanvas clean, consistent, and maintainable throughout its lifecycle.

Every new feature should follow these standards, whether implemented manually or generated with AI.
